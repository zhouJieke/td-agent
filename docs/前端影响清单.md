# 桌面链平台化改造 · 前端影响清单

> 2026-10-26 · 后端已完成桌面登录链平台化改造（企微接入、方案 A 移除、浏览器链企微删除）。
> 读者：deepseek-harness-desktop 前端开发。
> 完整对接说明：仓库 `td_business_center/docs/desktop-login-integration.md`（已同步重写）；
> 本文只讲**这次改了什么、前端要动哪里、哪些明确不用动**。

## 一、契约变化对照（旧版文档 → 现状）

| 项 | 旧契约 | 新契约 | 前端动作 |
|---|---|---|---|
| `begin` 入参 | 无请求体 | 可选 `{"platform":"dingtalk"\|"wecom"}`，**缺省 dingtalk**（不传 body 仍可用，向后兼容） | 双 tab 各传各自平台；请求带 `Content-Type: application/json` |
| `begin` 出参 | 四字段 `{nonce, claimKey, loginPage, authUrl}` | **三字段 `{nonce, claimKey, authUrl}`，`loginPage` 已删除** | 删除一切对 `loginPage` 的引用 |
| 二维码形态 | 方案 A（webview 加载 loginPage）/ 方案 B（自渲染 authUrl）二选一 | **钉钉与企微均使用 qrcode 自渲染 authUrl**（见第六节，2026-10-27 修订） | 原样编码后端 authUrl，不改写域名、路径和查询参数 |
| `GET /desktop/api/meta` | 存在（clientId + scope） | **已删除，返回 404** | 删除调用 |
| `POST /desktop/api/exchange` | 存在（内嵌页提交 authCode 用） | **已删除，返回 404** | 删除调用（方案 B 下前端本就不调它） |
| 支持平台 | 仅钉钉 | 钉钉 + 企业微信 | 企微 tab 接 `begin("wecom")` |
| `begin` 失败响应 | 未定义 | 400 `{"error":"invalid_request","error_description":"原因"}` | 捕获并展示 `error_description` |
| `claim` / `refresh` / token JSON | — | **完全不变**（202/200/410 语义、字段、形状都没动） | **无需改动** |

## 二、企微 tab 的可用性处理

- 后端配了 `hr.im.wecom`（corp-id）→ `begin("wecom")` 返回 `authUrl`，
  企业微信与钉钉共用 qrcode 生成二维码图片（见第六节），扫码后等待 claim
- 后端未配企微 → `begin("wecom")` 返回 400，文案「企业微信登录未配置（hr.im.wecom），
  无法发起」
- **没有**独立的"平台可用性探测"端点。建议：用户点企微 tab 时才调 `begin`，
  400 就展示后端文案（钉钉不受影响）；不要在登录页加载时预探测
- **不要**用 `GET /api/auth/im/platforms` 判断平台可用性——那是浏览器网页登录链的接口，
  桌面端不消费它，且它现在只返回 dingtalk

## 三、前端具体落点（对照 2026-10-26 代码现状）

1. **`src/ui/login/index.tsx` 的 `Login` 组件**（登录页壳已存在）：
   - 二维码目前是静态占位图（`/login/${provider}-preview-*.svg`）→ 改为
     `begin` 返回的 `authUrl` 经二维码库渲染（需新增 qrcode 依赖，如 `qrcode`）
   - 过期计时当前写死 180 秒是占位值 → 后端 nonce 有效期是 **5 分钟（300 秒）**，
     计时与「重新获取二维码」按钮对齐；授权成功后领取窗口 2 分钟
   - 钉钉/企微双 tab 布局已有，各自调 `begin(platform)`
   - 文案「界面预览 · 尚未连接企业认证服务」按接入进度更新
2. **请求走 Rust 侧**（`tauri-plugin-http` 或 reqwest，新增 invoke 命令）——
   webview 的 `fetch` 打后端是跨域，会被 CORS 挡
3. **claim 轮询**：每 1.5–2 秒一次；202 继续等、200 拿 token 完成、410 提示重新发起
4. **存储**：claimKey 与 token 存系统钥匙串（stronghold/keychain）；
   **refresh token 一次一换，每次必须保存返回的新值**
5. **登录成功出口**：`DesktopEntry` 的 `localMode` 切换到主界面

## 四、明确不用动的

- claim 轮询状态机（202/200/410 的判定与处理）
- refresh 协议、token JSON 的解析（字段名、形状完全没变）
- nonce / claimKey 的保存与配对逻辑
- `/desktop/cb`（手机 IM 回跳后端的地址，前端不参与）

## 五、联调自检顺序（后端部署后）

1. `POST /desktop/api/begin`（无 body）→ 200 三字段，authUrl 为钉钉授权链接
2. `POST /desktop/api/begin` body `{"platform":"wecom"}` → 未配企微时 400
   `invalid_request`；配置后 200 且 authUrl 为 wwlogin 链接
3. 真机扫码：两平台均将后端 authUrl 渲染为二维码 → 手机扫 → claim 由 202 变 200 拿到 token
4. 回归：`GET /desktop/api/meta`、`POST /desktop/api/exchange` 均 404（确认无残留调用）

## 六、企微二维码生成（2026-10-27 · 与钉钉共用 qrcode）

企业微信和钉钉统一使用 `begin` 返回的 `authUrl`，通过 `qrcode` 生成 SVG 图片，展示在原二维码区域。客户端不再改写为 qrConnect，不加载授权页 iframe，也不打开独立登录窗口。二维码内容保留后端返回的完整链接，手机端授权页面由后端提供的地址决定。

切换平台、`begin(platform)`、后端错误提示、每两秒 claim、410 自动重取、手动重新获取二维码、token 保存与刷新保持现有逻辑。两平台均在二维码生成成功后开始领取。
